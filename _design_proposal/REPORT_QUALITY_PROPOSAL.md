# 毎日レポートの内容設計 — 改善提案書

## 0. ユーザーが重視する観点

確認した重視軸を最上位の評価基準として固定する：

1. **新しさ** — その日でなければ書けない情報を優先
2. **被らなさ** — 過去レポートと同じテーマ・同じソースを避ける
3. **トレンド/重大ニュース** — 重要度に応じた階層化
4. **読みやすさ** — 構造の予測可能性、見出し設計、情報密度
5. **読む価値** — 後日参照したくなる技術ノートであること
6. **幅広さ** — 製品/技術/研究/業界動向、スピーカー全般を均等に
7. **事実ベース** — 一次ソース・出典必須、誇張表現を避ける
8. **論文原文** — 可能なら DL／取得不可でも要旨・arXiv ID は記録

---

## 1. 現状（SKILL.md v1）の問題点

54本のレポートと SKILL.md を実読して特定した課題：

### 1.1 「被らなさ」の検出粒度が荒い
- 現状の重複防止は `cited-urls-2026.txt` の **URL一致** のみ
- しかし**テーマ自体の重複**は検出されない。例：音響メタマテリアル特集が `2026-03-28`, `2026-04-24`, `2026-05-14` の3本に存在
- by-topic.md で見るとカテゴリ集約が機能していない（同じカテゴリに同テーマ反復）

### 1.2 検索の「広さ」が個別実行依存
- SKILL.md は「気になる技術領域を自由に探索」と書いてあり、毎回エージェントの選好に左右される
- 結果として、メタマテリアル・MEMS・Dolby Atmosなど "ホット" な領域が頻出し、地味な領域（測定機器、サブベース、磁気回路、振動板加工技術など）が薄くなる

### 1.3 論文原文 DL を試みていない
- WebFetch は使えるが、現SKILL.mdは「論文アブストラクト等の深掘りが必要な場合のみ使用」と消極的
- arXiv は **PDF・abs ページとも公開**で取得可。原文情報なしに引用するのは事実ベースと矛盾
- 結果として、Web検索結果の二次要約に依存し、伝聞情報が混じる

### 1.4 誇張表現を許容する文体
- SKILL.md には文体ガイドがなく、「次世代」「革命」「画期的」「最前線」「最強」などの語が頻出
- 5月19日レポートの theme：「**膜なき音の時代へ**：…」「**ポスト・ダイナミックドライバー時代の輪郭を描く**」など扇動的
- 業界紙のプレスリリースに同調しがちで、批判的視点が弱い

### 1.5 5セクション固定が画一化を招く
- 「特集 / 業界ニュース / 技術トレンド / 論文・特許・規格 / 未来予測」を**省略不可**としている
- そのため特集に値する材料がない日も「特集を捻り出す」状態になる
- 「未来予測 3方向 各 200〜400字」を強制 → 投機的・抽象的な記述が必須化 → 事実ベース志向と矛盾

### 1.6 重要度の区別がない
- 「重大ニュース」と「マイナー製品アップデート」が同列に並ぶ
- 業界ニュースセクションは300〜500字均等で書かれるため、本当に大きなニュースが埋もれる

### 1.7 frontmatter が Obsidian と協調しない
- タグは自由記述（既に 816個、表記揺れ 9グループ）
- 論文 (arXiv ID / DOI) は本文中だけで構造化されておらず、自動集計できない
- 言及エンティティ（企業・製品・概念）は本文中のみ

### 1.8 読者像が暗黙
- 一般向けニュースサイト風と、技術者向け仕様書風の中間で揺れる
- 読者像が「自分（=設計者・研究者）が後で参照する技術ノート」と明示されていない

### 1.9 字数制約が中身を圧迫
- 「特集 2500〜3500字」「業界ニュース 300〜500字 × 3トピック」など細かい字数指示
- 結果、情報が薄い日も水増しされ、濃い日も切り詰められる

### 1.10 過去レポートとの相互参照がない
- 既存54本を蓄積しながら、「以前カバーした件の続報」を明示する仕組みがない
- 例えば iwasemi OC-β は 2026-03-28 と 2026-04-24 の両方に登場しているが、後者から前者へのリンクがない

## 2. 改善方針（5つの設計判断）

### 2.1 「特集 + 巡回」の二本立てへ

| | 特集 (Feature) | 巡回 (Patrol) |
|---|---|---|
| 条件 | その日に**重大ニュース or 集中する複数ソース**が揃った日のみ | **毎日必須** |
| 役割 | 深掘りエッセイ、相互比較、技術考察 | 業界全体の地図、被覆性の担保 |
| 字数目安 | 必要に応じて 1500〜3500字 | 8〜12カテゴリ × 各150〜400字 |
| 省略 | **可**（特集に値しない日は省略） | 不可 |

→ 特集を毎日捻出する圧力をなくし、**日常はバランス重視の巡回で被覆性を担保**、特集は「これは特集すべき」という日に限定する。

### 2.2 巡回カテゴリの体系化（12カテゴリ）

毎日、以下の12カテゴリすべてに目を通す。**情報が無いカテゴリは「特筆事項なし」と明記**することで、被覆性を可視化する：

1. **製品 — HiFi / 民生** — スピーカー新製品、新型番、価格
2. **製品 — プロ/PA/スタジオ** — ライン・アレイ、モニター、ミックスバス
3. **製品 — カー/車載** — OEM搭載、アフター市場、車室内
4. **製品 — ポータブル/イヤホン/TWS/ヘッドホン** — トランスデューサ革新
5. **製品 — スマートスピーカー/サウンドバー/家電統合**
6. **技術 — ドライバー/振動板/磁気回路/エンクロージャ** — 材料・構造
7. **技術 — DSP/Class-D/ANC/ルームコレクション**
8. **技術 — 空間音響/Atmos/WFS/Ambisonics/Auracast**
9. **技術 — メタマテリアル/MEMS/CDT/プラズマ/ハプティクス**
10. **研究 — 論文 (JASA, AES, arXiv, IEEE)**
11. **研究 — 特許/規格 (USPTO, CTA, AES標準, IEEE)**
12. **業界 — M&A/決算/サプライチェーン/学会/展示会**

→ 既存54本のレポートを集計したところ「業界経営・M&A動向」「測定・解析・評価技術」「サブベース・低音再生」「環境音響・標準規格」は登場頻度が極端に低い。**カテゴリ強制で被覆性を保つ**。

### 2.3 論文原文取得ポリシー

論文取得の標準フローを以下に固定：

1. **arXiv ID が取れる場合**: `WebFetch https://arxiv.org/abs/XXXX.YYYYY` で abstract と図キャプションまで取得し、要約に反映
2. **DOI / 学会論文**: 出版社サイト abstract が公開なら同様に取得。ペイウォール時は abstract のみ
3. **特許**: USPTO / Google Patents 公開公報を取得
4. **規格**: AES / IEEE / CTA の発表ページ・規格番号と概要を取得
5. **取得不可の場合**: 「アブストラクト公開なし」と明示し、ニュース記事ベースの二次要約であることを記載

論文セクションには **必ず arXiv ID または DOI を frontmatter に構造化**：

```yaml
papers:
  - citekey: lissek2026cdt
    arxiv: 2508.18232
    doi: ""
    title: "Dual Corona Discharge Transducers for Broadband Directivity Control"
    venue: "Acta Acustica"
    year: 2026
    fetched: true        # 原文取得できたかフラグ
    priority: high       # 自分が読みたい優先度
```

### 2.4 文体ガイドライン（誇張禁止リスト）

**避ける語句**：
- 「革命」「画期的」「次世代」「最先端」「最強」「驚異の」「衝撃の」
- 「〜時代の幕開け」「〜を再定義」「常識を覆す」
- 「業界初」「世界初」（事実なら可・出典必須）

**好ましい表現**：
- 「2026年第1四半期出荷開始」「Acta Acustica 誌で発表」「先行モデル比 X dB 改善と報告」「メーカー資料による」「査読論文として公開」
- 数値・出典・発表媒体・日付を明示

**伝聞・推測の明示**：
- 「メーカー資料による」「業界紙の報道による」「公開情報からは確認できず」
- 自分の評価を入れる場合は「**評**:」「**コメント**:」セクションで分離

### 2.5 重要度タグ付け

各ニュースアイテムに重要度を付与：

```yaml
priority: critical    # 業界全体に影響する重大発表（M&A、規格制定、大手OEM搭載決定など）
priority: high        # 主要メーカーの新製品ライン、注目論文
priority: normal      # 通常製品アップデート
priority: minor       # 軽微なファームウェア・色違いなど（記録のみ）
```

巡回セクションでは `priority: critical/high` を中心に書き、`minor` は表でリスト化するのみで字数を割かない。

## 4. 「被らなさ」の二重ゲート

URL重複に加えて、**テーマ重複も検出**する：

### 4.1 URL重複（既存ロジックを維持）
`index/cited-urls-2026.txt` で重複URLチェック → 補足参照差し替え or テーマ再選定

### 4.2 テーマ重複（新規追加）
過去 N=21 日のレポートを参照し、**`feature-title` または `tags` の重複度** をスコア化：

```python
# 直近21日のレポートを取得
recent = fetch_recent_reports(days=21)

# 新レポートのタグ集合
new_tags = set(new_report.tags)

# 過去レポートのタグとのJaccard係数
for r in recent:
    overlap = len(new_tags & set(r.tags)) / len(new_tags | set(r.tags))
    if overlap > 0.4:
        warn(f"⚠️ {r.date} とタグ集合の重複度 {overlap:.0%}")
```

判定：
- 重複度 < 0.3 → ✅ PASS
- 重複度 0.3〜0.5 → ⚠️ 警告（特集テーマを変えるか、軸を切り替えるよう推奨）
- 重複度 > 0.5 → ❌ FAIL（特集を選び直す）

## 5. Obsidian Vault 統合（既設計との接続）

新フォーマットは [[DESIGN.md|Vault設計書]] と整合する：

- `entities-mentioned` frontmatter は、Daily Report からエンティティページへ wikilink を自動で張る
- `papers` frontmatter は `30_Literature/papers/{citekey}.md` のスタブ自動生成のトリガーになる
- `news-priority` 集計は Dashboard で可視化（critical/high の月次推移）
- 特集の「過去レポートとの関係」は [[]] wikilink で過去日付ノートと接続
- 巡回カテゴリは `covers-categories` で集計可能 → 月次の被覆率レポート

## 6. AI 動作変更（SKILL.md 改修ポイント）

以下を新 SKILL.md に組み込む：

1. **冒頭で読者像を明示**: 「読者はスピーカー設計者・研究者であるあなた自身。後日参照する技術ノートとして書く」
2. **モード判定**: 朝の検索結果を見て、特集に値するか判定 → feature mode か patrol-only mode を決定
3. **12カテゴリ全巡回を強制**: 各カテゴリ「特筆事項なし」明記可。被覆性ファースト
4. **論文原文取得を標準化**: arXiv IDがあれば WebFetch で abs ページを取得して引用、frontmatterに `fetched: true/false` 記録
5. **誇張禁止リスト**: 文体ガイドラインを冒頭に置く
6. **テーマ重複ゲート**: 21日のwindowでJaccard係数チェック追加
7. **重要度タグ付け**: 各ニュースに priority 付与
8. **「未来予測」削除→「Open Questions」任意化**
9. **エンティティ言及の構造化**: frontmatterの `entities-mentioned` 配下に集約
10. **過去レポートへの相互参照セクション必須化**: 1〜3件 wikilink で明示

## 7. 移行リスクと段階

### 7.1 段階導入案
- **Phase A（即時）**: 文体ガイドライン・誇張禁止・読者像の明示 だけを既存SKILL.mdに加える（差分小）
- **Phase B（2週間後）**: 12カテゴリ巡回モードを追加、特集任意化
- **Phase C（1ヶ月後）**: frontmatter v2 + 論文原文取得標準化
- **Phase D（Vault化と同時）**: entities-mentioned, papers, news-priority の構造化

### 7.2 既存54本との互換性
- 既存レポートの frontmatter は変えない（読み取り側で v1/v2 を判別）
- 新フィールドはすべて optional として導入
- by-topic.md, cited-urls-2026.txt は継続運用

### 7.3 月次レビュー
- 月初に過去30日のレポートを集計：
  - 各カテゴリの被覆率（巡回が「特筆事項なし」連発になっていないか）
  - 特集モード率（多すぎず少なすぎず）
  - 論文原文取得率（fetched: true の割合）
  - 重要度分布（criticalが多すぎるとインフレ警報）

## 8. 改善後の「読む価値」とは何か

これらの改善は、最終的に**6ヶ月後の自分**がレポートを読み返したときに：

- 「2026年5月のCDT論文は何だっけ？」→ `papers` frontmatterから1秒で特定
- 「あのときのKEF新製品は？」→ [[KEF]] backlinkで一覧
- 「メタマテリアルの動向の変遷は？」→ MOC_Metamaterial のDataviewブロックで時系列
- 「3月の特集と今月の特集の違いは？」→ 各特集の「過去レポートとの関係」セクション

を実現できることを目標とする。新しさ・被らなさ・トレンド性は、長期的な参照価値の前提条件であり、目的そのものではない。
